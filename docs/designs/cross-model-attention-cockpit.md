## Problem Statement

CLI Lane can prove whether a tmux-managed process is alive, dead, stopped, or failed. It cannot tell whether an agent is working, idle, waiting for input, or blocked on approval. An operator running 5–15 Claude, Codex, and Kimi sessions must repeatedly inspect panes or keep Claude Agent View open just to find the next interruption.

The v0.6 product is a cross-model attention cockpit. It must answer three questions without lying:

1. Which lane needs me now?
2. What exactly is it waiting for?
3. Which native lane should I attach to?

The initial user is Ming. Broader open-source demand remains unproven, which is acceptable for a personal-first release.

## What Makes This Cool

CLI Lane becomes a local human-interrupt router rather than another process list. It ranks attention requests, shows a bounded adapter-provided request summary, and jumps to the correct native lane in one keystroke. Attaching becomes the escape hatch instead of the normal monitoring loop.

The differentiator is not a new chat UI. It is the combination of CLI Lane's durable process identity with semantic state whose source is always visible. A hook event, an ACP session update, an inference, and a stale adapter are never presented as equally trustworthy.

The ground this design claims is precise. Rival monitors — cctop, ccboard, AgentMonitor — already join agent sessions to local processes, but heuristically: transcript scanning, working-directory matching, hook-state inspection, and mostly for Claude Code alone. A heuristic join breaks the moment two sessions share one directory; a key injected at spawn time cannot. And none of these tools exports the join as structured telemetry. The claim here is therefore a deterministic join, never the first join: one spawn-time `task_generation` binds the registry record, the managed process, the provider session, and the vendor telemetry stream, for every provider CLI Lane launches.

The approved interaction sketch was reviewed out of band and is not tracked.

```text
┌ Ranked interrupt queue ───────────────┬ Selected request ───────────────┐
│ 1 Claude  APPROVAL  hook/exact   8m  │ Bounded request summary          │
│ 2 Codex   INPUT     app-server   3m  │ Recent output preview            │
│ 3 Kimi    WORKING   pane/inferred     │ [attach]                         │
│ 4 Kimi    UNKNOWN   adapter stale     │ Source health and event age      │
└───────────────────────────────────────┴─────────────────────────────────┘
  j/k move   enter attach   n next   f filter   ctrl-q detach
```

## Constraints

- Native Claude, Codex, and Kimi terminals remain first-class. CLI Lane does not replace their provider-specific commands or conversation interfaces.
- ACP-backed sessions are optional. A provider without a proven ACP adapter remains a native lane.
- CLI Lane remains a process runtime and attention layer. Queues, DAGs, autonomous retries, budgets, and agent directors stay above it.
- Existing `run`, task records, lifecycle states, logs, fleet reads, and tmux identity checks remain backward compatible.
- The implementation stays Python 3.10+ standard library plus tmux. SQLite is available through Python's standard library; no new package dependency is required.
- Semantic state may come from structured provider events or labeled inference. Insufficient evidence becomes `unknown`; it never becomes a confident guess.
- v0.6 is local-host first. Remote fleet attention is read-only follow-up work, not part of the first release.
- Clean launch profiles reduce accidental credential inheritance. They are not a sandbox and do not defend against a malicious process running as the same Unix user.
- v0.6.0 is observation plus attach. Provider-native reply and approval are held for v0.6.x and require a separate compare-and-act contract with provider acknowledgement; raw tmux paste is never an approval transport.
- The merged v0.5 hub must have a tagged, tested, installed release before v0.6 implementation starts.

## Premises

1. “Replace Agent View” first means replacing its daily attention loop, not cloning Claude's supervisor, worktree, dispatch, or resume machinery.
2. Native lanes plus optional ACP sessions provide a better migration path than either ACP-only or terminal-inference-only operation.
3. Every semantic state carries provenance: `native_hook`, `acp`, `inferred`, or `unknown`.
4. Existing task lifecycle and new semantic attention state are separate axes and separate storage contracts.
5. Environment allowlisting is part of the agent launch contract, not deferred hardening.
6. Quality measures both false alerts and missed blockers. Authoritative sources must be exact; inferred sources need measured precision and recall; uncertainty remains visible.

## Cross-Model Perspective

The independent Codex review agreed that the product should be a “human interrupt router,” not another dashboard. It identified Fleet as roughly half of the interaction model, while CLI Lane's durable identity, recovery, provenance, hybrid native/ACP support, and clean launch boundary form the missing half.

Codex recommended one complete vertical slice: an append-only semantic event stream, a deterministic reducer, one authoritative Claude source, one Codex source, a blocked-first attention view, one-key jump, persistent reconstruction, and environment allowlisting.

It challenged the original “zero false alerts during one hour” criterion because a system can satisfy it by suppressing uncertain alerts. The accepted revision measures precision and recall and preserves `unknown` as an honest state.

## Approaches Considered

### Approach A: Minimal native overlay

Rejected because it ships fastest but risks turning provider-specific hooks and terminal inference into the permanent architecture.

### Approach B: Hybrid attention core

Chosen because one provider-neutral event and state contract can serve native hooks and optional ACP sessions while preserving CLI Lane's terminal-first behavior.

### Approach C: CLI Lane runtime with Fleet as the cockpit

Rejected as the primary product direction because it gives another project control of CLI Lane's operator surface and may not preserve CLI Lane's lifecycle guarantees. Fleet remains a reference for interaction patterns and a possible downstream consumer of CLI Lane's JSON state.

## Recommended Approach

### Product boundary

Ship `clilane attention` above the existing task runtime. `clilane hub` remains the raw launcher and pane switcher.

Stage the release so independently risky boundaries do not land at once:

1. **v0.5.1 prerequisite:** clean named launch profiles, released and used by agent presets.
2. **v0.6.0:** structured observation, durable reduction, ranked Attention View, JSON reads, and attach. No provider mutation and no inference-driven alert claims. The same release adds the launch-time `OTEL_RESOURCE_ATTRIBUTES` injection defined under *Telemetry-native identity export* — additive to the v0.5.1 environment contract — and persists the registry/ledger binding the agent-usage-manager probe consumes; the probe itself ships on that consumer's own schedule and gates nothing here.
3. **v0.6.x:** provider-native reply or approval only after a separate compare-and-act contract passes replay, acknowledgement, and race tests. Qualified inferred adapters may rank alerts only after meeting the evaluation gate.

No provider is promised authoritative support before the Phase 0 capability spike. A provider that fails the gate remains visible as a running task with semantic state `unknown` and attach-only behavior. v0.6.0 may claim the Agent View attention-loop replacement only if both Claude and Codex prove authoritative open and close events for input and approval requests plus turn activity and source health. If either fails, ship the work only as an experimental preview. Kimi may remain unknown in v0.6.0 and is excluded from supported-lane blocker guarantees until it passes the same gate.

### System shape

```text
 provider hook ───────┐
 ACP session adapter ─┼──> one active adapter instance ──> validated ingest
 labeled inference ───┘          │                    ├─ events
                                 │                    ├─ requests
 adapter heartbeat/error ────────┤                    ├─ source health
 existing task registry ─────────┴───────────────> deterministic reducer
                                                          │
 independent labels ─────────────────────────────> evaluation only
                                                          ▼
                                                  clilane attention
                                                  ├─ ranked queue
                                                  ├─ provenance/health
                                                  ├─ bounded preview
                                                  └─ attach
```

The existing task registry remains the source of truth for process identity and lifecycle. The attention ledger links semantic state to `task_id`; it does not replace or migrate task records.

### Attention ledger

Use one SQLite database per CLI Lane tmux socket under the existing mode-0700 local state root: `attention/<socket-digest>.sqlite3`. Derive the digest with the same socket-name function as the task registry. The database and its WAL files are mode 0600. Python's standard-library `sqlite3` module preserves the project's zero-package-dependency constraint.

The attention database is supported only on a local filesystem. Initialize or migrate it under a permanent per-socket attention lock. Pin `PRAGMA user_version=1`, `journal_mode=WAL`, `synchronous=FULL`, foreign keys on, and a 50 ms busy timeout. Every ingest uses `BEGIN IMMEDIATE`; failure to acquire the writer lock returns nonzero without delaying the provider turn indefinitely.

The database has four logical records:

- `events`: immutable semantic observations within the active retention window;
- `requests`: current and recently closed input or approval requests;
- `adapters`: source identity, capabilities, heartbeat, freshness, and bounded error state;
- `snapshots`: the latest total reduction per task for fast reads.

Adapter input and trusted persisted fields are separate. An adapter submits:

| Field | Purpose |
|---|---|
| `schema_version` | Reject unknown adapter payload shapes. |
| `event_id` | Globally unique idempotency key. |
| `task_id` | Links the event to CLI Lane's durable task identity. |
| `task_generation` | Binds the event to the exact CLI Lane process generation. |
| `adapter_instance_id` | Identifies the one registered adapter instance for this task generation. |
| `source_session_id` | Binds the provider conversation or ACP session. |
| `source_event_id` | Deduplicates provider retries. |
| `kind` | Exact event enum defined below. |
| `occurred_at` | Provider observation time, used only for display and latency measurement. |
| `request_id` | Required only for request events. |
| `payload` | Kind-specific bounded object. |

Trusted internal producers use a smaller input schema: deterministic `event_id`, task id, task generation, internal kind, and bounded payload. They do not supply adapter or provider-session identity. `task_terminal` uses source `process_registry`; freshness and maintenance transitions use source `attention_core`.

Trusted ingest validates either input shape, then adds these persisted columns:

| Field | Purpose |
|---|---|
| `ledger_seq` | Transactionally assigned local integer ordering used for replay. |
| `provider` | Adapter provider, or null for internal process events. |
| `source` | `native_hook`, `acp`, `inferred`, `process_registry`, or `attention_core`. |
| `received_at` | Local ingest time used for freshness, never replay ordering. |
| `summary` | Control-stripped operator-facing reason, maximum 512 UTF-8 bytes. |

`task_generation` is the lowercase SHA-256 of the task record's socket, task id, creation timestamp, and tmux session joined with NUL bytes. CLI Lane computes and injects it; adapters cannot choose it.

Exact event enum and payload rules:

| Kind | Required payload | Effect |
|---|---|---|
| `adapter_registered` | adapter version, source, capabilities | Claims the active adapter slot in `recovering`. |
| `adapter_ready` | recovered-request count, `fresh_for_seconds` | Declares recovery complete and advances health to `healthy`. |
| `adapter_heartbeat` | `fresh_for_seconds` | Advances freshness for an already ready adapter. |
| `adapter_closed` | close code | Marks the source stale immediately and releases it for replacement. |
| `adapter_error` | stable error code, bounded message | Records source failure. |
| `source_stale` | prior `fresh_until` | Internal idempotent transition generated when freshness expires. |
| `turn_started` | optional non-request summary | Sets working when no request outranks it. |
| `turn_idle` | optional non-request summary | Sets idle when no request outranks it. |
| `request_opened` | request kind `input` or `approval`, display digest, optional display text, recovery flag | Opens one exact request; `recovered: true` is valid only while its adapter is recovering. |
| `request_resolved` | resolution code | Closes the exact request. |
| `request_expired` | expiry code | Closes the exact request. |
| `request_cancelled` | cancellation code | Closes the exact request. |
| `task_terminal` | outcome `done`, `stopped`, or `failed` | Internal event from the task registry; closes every open request. |

Persist external rows with non-null adapter instance, provider session, and provider event identity. Persist internal rows with those columns null and a deterministic internal `event_id`; a database `CHECK` constraint enforces the two shapes. `source_stale` identifies its target adapter instance and prior deadline inside its trusted payload. Enforce uniqueness on every `event_id` and, for external rows, `(task_id, task_generation, adapter_instance_id, source_session_id, source_event_id)`. `requests` uses `(task_id, task_generation, adapter_instance_id, source_session_id, request_id)` as its primary key; `snapshots` uses `(task_id, task_generation)`; adapter instances are unique by id and one row per task generation is marked active. Event insert, request transition, and snapshot reduction occur in one transaction. Duplicate events are no-ops. Invalid, oversized, unknown-schema, stale-generation, inactive-adapter, or invalid-transition events exit nonzero and write nothing; they produce bounded stderr diagnostics rather than a quarantine row.

An open request is identified by `(task_id, task_generation, adapter_instance_id, source_session_id, request_id)`. It stores request kind, open or closed status, opened and closed ledger sequence, a digest, and an optional control-stripped display string capped at 2 KiB. That string is the only request content retained by Attention View; it is erased 24 hours after closure. Event rows keep only the digest. Multiple requests may coexist.

Events are append-only only inside the active window. A deterministic maintenance transaction prunes closed requests and terminal-task events older than 30 days, then targets a soft budget of 100,000 events per socket by removing the oldest eligible terminal-task history. Open requests and events for live tasks are never pruned, so the budget is not a hard cap. Attention View and JSON emit a storage warning above the budget. Automatic maintenance does not run `VACUUM`.

Do not store raw prompts, transcripts, environment values, or model credentials in the ledger. Event `summary` is forbidden on every request event; request display content exists only in the short-lived `requests.display_text` field. Existing raw terminal logs remain the explicit preview source.

### State model and reducer

Process lifecycle and semantic state remain separate:

| Axis | Values |
|---|---|
| Process | existing `initializing`, `running`, `stopped`, `succeeded`, `failed` |
| Semantic | `working`, `needs_input`, `needs_approval`, `idle`, `done`, `stopped`, `failed`, `unknown` |
| Attention | `yes`, `no`, `unknown` |
| Provenance | `process_registry`, `native_hook`, `acp`, `inferred`, `unknown` |

Replay strictly by `ledger_seq`; provider timestamps never break ties. The reducer is total:

1. When registry reconciliation observes process `succeeded`, `stopped`, or `failed`, trusted ingest writes one idempotent `task_terminal` event. In the same transaction it closes every open request with reason `task_terminal`, maps semantic state to `done`, `stopped`, or `failed`, sets attention `no`, health `not_applicable`, and provenance `process_registry`.
2. For a live process, the oldest open authoritative approval request yields `needs_approval`; otherwise the oldest open authoritative input request yields `needs_input`. The snapshot exposes the selected request plus the total open-request count.
3. A request opens only from a valid request-open event. It closes only from a resolution, expiry, or cancellation event carrying the exact five-part request identity. Closing an absent or already closed request is an idempotent no-op.
4. With no open authoritative request, the latest authoritative turn transition by `ledger_seq` yields `working` or `idle`. Equal-authority conflicts are last-committed-wins because `ledger_seq` is total.
5. A qualified inferred adapter may open or close its own inferred request and yield inferred `working`, `idle`, `needs_input`, or `needs_approval`. An unqualified inferred request is retained for evaluation but yields semantic and attention `unknown`. No inferred event may open, clear, or outrank an authoritative request from the active adapter instance.
6. Adapter health is `recovering`, `healthy`, `stale`, `error`, `unsupported`, or terminal-only `not_applicable`; output also uses `absent` when no adapter exists. Registration enters `recovering`. Only `adapter_ready` can enter `healthy`; `adapter_heartbeat` before readiness is invalid. A ready or heartbeat event records `fresh_until`, capped at five minutes after receipt. Expiry reconciliation observes the exact prior deadline, then inserts `source_stale` only when the adapter is still active, its health is still `healthy`, its stored `fresh_until` still equals that deadline, and local time has crossed it. A racing heartbeat changes the deadline, so the stale compare-and-set becomes a no-op. `adapter_closed` writes an immediate sequenced stale transition. Freshness therefore changes only through events. If a source is recovering, stale, or in error with no open request, semantic and attention state are `unknown`. If a request is still open, semantic state remains the request state but attention becomes `unknown`.
7. No valid semantic evidence yields `unknown`. A stale task generation, provider session, duplicate event, malformed event, or future schema version cannot change the snapshot.
8. Each snapshot stores the last reduced `ledger_seq`, reducer version, source health, semantic state, attention state, provenance, selected request identity, open-request count, and update time. Events do not carry reducer versions. When code increments the reducer version, it replays retained events for live tasks under the new reducer into a candidate snapshot, then commits atomically. Replaying the same ordered retained events under the same reducer must reproduce the same snapshot bytes except for explicitly excluded maintenance timestamps.

The total live-task output table is:

| Requests/evidence | Health | Semantic | Attention | Provenance | Selected request |
|---|---|---|---|---|---|
| Open authoritative approval | healthy | `needs_approval` | `yes` | active adapter source | oldest approval |
| Open authoritative input, no approval | healthy | `needs_input` | `yes` | active adapter source | oldest input |
| Open authoritative request | stale or error | request state | `unknown` | active adapter source | oldest by approval then input |
| Qualified inferred request, no authoritative request | healthy | inferred request state | `yes` | `inferred` | oldest qualified inferred request |
| Unqualified inferred request, no authoritative request | any | `unknown` | `unknown` | `inferred` | none |
| No request, latest authoritative turn | healthy | `working` or `idle` | `no` | active adapter source | none |
| No request, qualified inferred turn only | healthy | inferred `working` or `idle` | `no` | `inferred` | none |
| No request | recovering | `unknown` | `unknown` | active adapter source | none |
| No request | stale or error | `unknown` | `unknown` | active adapter source | none |
| Unsupported adapter or no semantic evidence | unsupported or absent | `unknown` | `unknown` | `unknown` | none |

Terminal process rows use rule 1 and do not consult this table.

### Adapter boundary

Each adapter registration declares:

- provider and adapter version;
- supported event kinds;
- whether each event is authoritative or inferred;
- heartbeat or freshness behavior;
- v0.6.0 capability `observe`; later capabilities `reply`, `approve`, or `cancel` are informational until their mutation contract is released;
- provider session identity and recovery behavior;
- a random `adapter_instance_id` plus monotonically increasing adapter epoch.

Exactly one adapter instance is active per task generation. The launch profile selects native hook, ACP, or inference; those sources do not run concurrently for the same generation. Native hooks call a bounded `clilane attention emit` interface with identity supplied at launch. ACP adapters subscribe to structured session updates and translate them into the same event contract. Terminal or transcript observers may emit inferred evidence but cannot impersonate an authoritative source.

Registration transactionally claims the active slot. Before deciding replacement eligibility, the registration transaction runs the same exact-deadline expiry reconciliation as a reader; replacement does not depend on Attention View being open. A replacement may claim only when the prior instance explicitly closed or that reconciliation has persisted `source_stale`. Replacement increments the epoch, closes prior-instance requests as `adapter_replaced`, supersedes the old instance, and records the new instance as `recovering`; subsequent old-instance events are rejected.

The recovering adapter re-emits each unresolved request as `request_opened` with `recovered: true` under its new five-part identity. New live requests and turn transitions are invalid while recovering. It then submits `adapter_ready` with the recovered-request count and freshness window. In one transaction, ingest verifies that the declared count equals the instance's open recovered requests, writes the ready event, and advances health and `fresh_until`. A mismatched count, heartbeat before readiness, or non-recovery semantic event before readiness fails closed. Until that commit, semantic and attention state remain `unknown`. There is no multi-source arbitration inside one task generation.

An adapter is **authoritative** only for event kinds emitted by a documented provider hook or structured protocol and proven by fixtures to bind the exact task generation, provider session, and request identity. An adapter is **supported** only after every event kind it claims passes deterministic transition, duplicate, reconnect, stale-session, and latency tests. A request is **current** only while its exact identity is open in the latest snapshot. Evidence is **fresh** only before the adapter's stored `fresh_until` and while task and provider session identities still match.

Heartbeat and adapter-error events update the `adapters` record. Errors use a stable code plus a control-stripped message capped at 256 bytes. Unsupported providers explicitly register `unsupported`; they do not masquerade as stale.

### Attention View

`clilane attention` is a keyboard-first full-screen terminal view for observation plus attach.

- order lanes by the total tuple `(rank_bucket, rank_subkind, rank_seq, task_id)`;
- show provider, project, concise reason, age, semantic state, and provenance on every row;
- show bounded recent output and source health for the selected lane;
- support `j/k`, attach, next interruption, filter, and detach;
- strip ANSI and control characters from summaries, previews, and JSON strings before rendering;
- offer `clilane attention --json` as the stable read-only integration surface.

Rank buckets are: 0 healthy authoritative approval; 1 healthy authoritative input; 2 qualified inferred approval; 3 qualified inferred input; 4 stale or error request; 5 unknown or source-problem lane without a request; 6 working; 7 idle; 8 failed; 9 stopped; 10 done. Buckets 0-3 use `rank_subkind = 0`. Bucket 4 uses approval `0`, input `1`. Bucket 5 uses error `0`, stale `1`, recovering `2`, unsupported `3`, and absent semantic evidence `4`; the last classification also covers a healthy adapter that has not emitted valid semantic evidence. Buckets 6-10 use `rank_subkind = 0`.

For request buckets, `rank_seq` is the selected request's opening sequence ascending. For bucket 5, it is the sequence of the last applicable health or evidence event ascending so the oldest unresolved source problem appears first; a lane with no ledger event uses the sentinel `2^63 - 1`. For working, idle, and terminal buckets, it is the negative last ledger sequence so recently active lanes appear first. `task_id` is always the final stable tie-breaker. This defines a total key even for raw tasks, unsupported providers, and lanes with no event. A healthy input therefore outranks a stale approval, matching the reducer's health rule.

Implement the interactive surface with Python standard-library `termios`, `tty`, `selectors`, and ANSI output. It requires a TTY, uses the alternate screen, restores terminal settings in `finally` and on handled termination signals, rerenders on `SIGWINCH`, uses ASCII-safe clipping instead of assuming Unicode display width, and supports nested tmux. Non-TTY invocation requires `--json`.

`--json` emits one object with `schema_version: 1`, `generated_at`, `complete`, nullable top-level `error`, and a `lanes` array in the exact rank order above. Every lane includes task id, task generation, name, provider, project, process state, non-null semantic state, nullable reason, attention state, provenance, source health, nullable event age, nullable selected request identity, open-request count, and `actions: ["attach"]`. Semantic state uses `unknown`; it is never null. Timestamps are RFC 3339 UTC strings. Exit 0 means a complete snapshot, exit 1 means invalid invocation or unreadable state with no usable payload, and exit 2 means valid partial JSON with `complete: false`.

v0.6.0 never infers that a lane is safe to receive raw text. Attach opens the provider's native terminal. A future reply or approval transport must call the provider's structured API using `(task_generation, adapter_instance_id, source_session_id, request_id, snapshot_revision, action_id)`, receive an explicit acknowledgement, and be idempotent. It never delegates mutation to generic `send` or `key`.

### Clean launch profiles

Add `~/.config/clilane/profiles.json`, capped at 256 KiB. It must be a regular non-symlink file owned by the current uid and not writable by group or others. Profiles and all hub schema versions use one strict JSON decoder: duplicate keys at any object level, non-finite numbers, integers longer than the existing 64-digit limit, and a `schema_version` whose exact type is not integer fail validation. Unknown fields, duplicate profile names, invalid environment names, relative fixed working directories, empty commands, and unsupported schema versions fail before tmux starts. Ambiguous legacy hub v1 documents are rejected rather than receiving last-key-wins compatibility. Provider labels use the existing safe-name grammar rather than a closed enum; Phase 0, not profile parsing, determines support.

Version 1 shape:

```json
{
  "schema_version": 1,
  "profiles": {
    "claude-default": {
      "provider": "claude",
      "command": ["claude"],
      "cwd": {"mode": "explicit"},
      "env": {
        "inherit": ["SSH_AUTH_SOCK"],
        "set": {}
      }
    }
  }
}
```

`cwd.mode` is `explicit`, which requires an explicitly supplied `-C`, or `fixed`, which requires an absolute path in the profile and forbids `-C`. Profile lookup is exact and case-sensitive. Profiles are a reusable launch-security boundary, not hub presentation data: `clilane run NAME --profile PROFILE [-C DIR]` and hub presets both resolve the same standalone profile document. `--profile` and a raw `-- COMMAND` are mutually exclusive. Profile schema v1 is launch-only and does not name an adapter; adapter identity remains unproven until Phase 0 and may be added only after the evidence matrix qualifies that contract.

Before adding profile mode, consolidate `clilane run` parsing into one dedicated parser that splits the raw tail at the command sentinel and returns one typed launch request. It preserves the existing compatibility that accepts run options before or after `NAME`, but each option is interpreted exactly once. The request records whether `-C` was explicit and centrally enforces raw-command/profile exclusivity, `--timeout` requiring `--wait`, and fixed-versus-explicit profile cwd rules; execution does not merge a second parsed representation.

Every entry point then resolves to one complete typed `LaunchSpec` before calling `run_task`. A shared validator rejects empty or NUL-bearing argv items, invalid cwd and environment values, malformed environment names, collisions with CLI Lane-owned keys, missing required values, and incompatible raw, profile, cwd, wait, timeout, or on-exit modes. Validation completes before task ids are allocated or any task record, log, supervisor, or tmux session is created. Hub v1, hub v2, raw CLI, and profile launches do not retain separate late-validation paths.

Hub schema version 1 keeps its existing `{name, command, dir}` data shape and ambient-environment launch semantics. Its validation changes only by joining v2 and profiles on the strict JSON decoder and the 256-KiB bounded read; profile-only owner, mode, type, and symlink rules do not apply to hub files. Hub schema version 2 permits each preset to contain exactly one of `command` or `profile`; mixing them fails validation. A profile preset supplies `dir` only when its profile uses `cwd.mode: explicit`; it omits `dir` for a fixed profile. Hub menu rendering resolves the selected preset and profile, then passes the exact preset name plus a SHA-256 digest of canonical UTF-8 JSON with sorted keys, compact separators, and no ASCII escaping through the tmux callback. Launch re-reads both documents, selects by exact name, recomputes the digest, and fails with a reopen-menu error before task-record creation if the name, profile, directory, command, or environment policy changed. Array indexes are not durable selection identities. Existing v1 presets continue to work without automatic rewriting, but any agent preset intended for Attention View must use a v2 profile reference.

Launch validation occurs before task-record creation. Open the profile path without following symlinks, then validate ownership, mode, regular-file type, and size from the open file descriptor; resolving a path before validation is insufficient because it hides a symlink. Build the child environment from the present `HOME`, `PATH`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `LANG`, `LC_ALL`, and `LC_CTYPE` values when set; missing optional baseline variables are omitted. Every exact name in `env.inherit` is unique and required: duplicates, missing variables, and NUL-bearing values fail validation instead of being silently omitted. Apply `env.set` only after all inherited dependencies validate. Reject secret-looking keys in `env.set` whose names end case-insensitively in `_TOKEN`, `_KEY`, `_SECRET`, or `_PASSWORD`; secrets must come from provider-owned files or an explicitly inherited key. One centralized owned-key set rejects exact `TERM`, `TMUX`, and `TMUX_PANE` plus `CLILANE_` and legacy `AGT_` prefixes in both `inherit` and `set`. v0.5.1 injects only CLI Lane-owned routing and task identity required by the current runtime; it neither injects nor merges OTel attributes. The versioned OTel merge rule below is a proposed v0.6-only exception and remains outside this reduced review. No other ambient key is inherited.

Launch code passes that child environment as an explicit mapping. The hub environment loader returns its captured legacy mapping without clearing or rewriting process-global `os.environ`; raw launches snapshot the existing legacy environment, while profile launches construct the allowlisted environment from their caller mapping. One `run_task(..., environment=...)` path and one `set_task_environment(session, environment)` path own task creation, tmux setup, cleanup, and logging for both modes. Environment installation reads current tmux state once, computes a deterministically ordered delta, and applies all removals and assignments through one bounded tmux command queue; it never starts one subprocess per key or embeds a second environment transport in the supervisor command. Tests assert constant tmux RPC count as key count grows rather than relying on a flaky millisecond benchmark. No launch path temporarily mutates global environment state or duplicates task lifecycle logic.

### Telemetry-native identity export (OTel)

Review status: preserved amendment, not cleared by the 2026-08-23 reduced engineering review. Do not implement this subsection under tasks T1-T9. The accepted P1 TODO requires a separate review after v0.5.1 and the Phase-0 capability matrix.

The hook-plus-registry binding remains the primary session↔process mechanism. This subsection adds a second, telemetry-native transport for the same identity. It is strictly additive: its absence or failure never weakens the primary binding, and no second identity is introduced.

At spawn, CLI Lane injects `OTEL_RESOURCE_ATTRIBUTES=clilane.task_generation=<hash>` into the managed child environment of every launch, raw or profile, because every task record carries the hash inputs. `<hash>` is the exact `task_generation` already defined for the attention ledger. The injection rides the one environment path both launch modes share: the child mapping is pushed into the tmux session environment by `set_task_environment()` (`bin/clilane:1688-1703`, called at `:1931`) and reaches the provider process when the `supervise()` child branch execs (`os.execvpe` at `bin/clilane:980`). If the variable is already present — possible only through an explicit profile `env.inherit` entry or a raw launch's legacy snapshot — CLI Lane merge-appends its pair to the existing comma-separated list per OTel environment-variable semantics, ordered so the launcher value wins under the SDKs' last-wins duplicate-key convention. Operator-supplied attributes under other keys pass through untouched.

Rationale: Claude Code's OTel stream carries `session.id` plus custom resource attributes on every exported metric and event by default, so the (`task_generation` → `session.id` → pid) triple falls out of the vendor's own telemetry with no sidecar, transcript scan, or directory heuristic. Because the registry already persists every hash input (`socket`, `id`, `created`, and `session` are all in `RECORD_FIELDS`, `bin/clilane:104-115`), any consumer can recompute `task_generation` without a registry schema change.

Per-lane support is a requirement to verify, not a claim:

- Claude Code: resource attributes ride its documented OTel stream; the Phase 0 spike confirms the exact attribute and `session.id` field names on the pinned provider version.
- Gemini CLI (not a Phase 0 provider): honors `OTEL_RESOURCE_ATTRIBUTES`, verified at its pinned OTel SDK dependency; a Gemini lane gets the telemetry join with no adapter work.
- Codex CLI: resource-attribute support is source-inferred only. An empirical check must pass before the README or this design may claim it; until then Codex joins through the hook and registry layer alone.
- Kimi Code: has no OTel lane at all; hook plus registry binding only.

### Recovery and failure behavior

Attention View startup performs these one-time steps:

1. Read the existing task registry.
2. Open the attention ledger, verify `user_version`, and run `PRAGMA quick_check` once before any view reads.
3. Reconcile snapshots with current task identities and replay retained events when the reducer version changed.
4. Run deterministic retention maintenance without resurrecting removed tasks.
5. Acquire the single interactive-watcher lease for this socket, then bind `control/attention-<socket-digest>.sock` as a mode-0600 Unix datagram endpoint. The lease records the watcher PID and OS start identity; only a proven-dead owner permits stale endpoint cleanup. A second interactive view refuses rather than replacing a live watcher. `--json` does not acquire this lease.

After each committed ingest, the writer sends one nonblocking best-effort byte to the watcher endpoint. Missing, full, or racing endpoints never roll back a committed event. The TUI uses `selectors` over stdin and the datagram socket, with a 100 ms timeout as the fallback registry/freshness poll. Each wake or timeout:

1. reads the registry without holding its lock across SQLite work;
2. reconciles process identity and snapshot state;
3. marks live tasks without valid semantic evidence as unknown;
4. ingests the idempotent internal `task_terminal` event when a process first becomes terminal, closing its requests in the same transaction;
5. for every crossed `fresh_until`, attempts the exact-deadline `source_stale` compare-and-set before rendering; and
6. renders from the resulting committed snapshot.

The watcher removes only its own socket and lease in `finally`. A crash leaves a reclaimable endpoint whose recorded PID/start identity must be proven dead before removal. `--json` performs startup validation and the same reconciliation once, including expiry compare-and-set, but does not run a watch loop. `PRAGMA quick_check` is never part of a watch tick. Registry polling and attention transactions never hold the existing registry lock while waiting on SQLite, avoiding lock-order inversion.

Schema creation and future migrations are transactional and serialized by the attention lock. An unknown schema version or failed integrity check disables Attention View and reports the exact database path; it never auto-deletes or replaces the database. The operator may preserve or move it aside and start a fresh unknown-state ledger. Existing `run`, `status`, `attach`, `stop`, and `rm` continue to work.

The production ledger cannot reveal missed events by itself. Evaluation uses an independent mode-0600 labeled JSONL stream produced by the dogfood harness or a human label command. Each label binds task generation, expected semantic state, start and end time, and optional request kind. The reducer never reads labels. Evaluation joins adapter output against labels and reports precision, recall, unknown coverage, observation latency, and ingest-to-view latency.

### Consumer contract: agent-usage-manager probe

The identity binding has one designated downstream consumer at design time: agent-usage-manager, the fleet's per-agent process telemetry collector. Its collector today reads only `pid`, `ppid`, `name`, `status`, `create_time`, and `cmdline` from the process table and derives a per-agent label through a precedence chain: tmux label, then launchd label, then the base matcher. Every step of that chain is heuristic and shares the failure mode named in the positioning note above — two sessions in one directory are indistinguishable.

The amendment adds one probe to that collector, at design level. The probe reads CLI Lane's task registry, recomputes `task_generation` from each record's socket, task id, creation timestamp, and tmux session, and maps the record to its live process through the same tmux session and pane identity CLI Lane already maintains. Once hooks report provider sessions, the probe also reads `source_session_id` from the attention ledger so a row can carry the provider conversation identity. In the precedence chain, a clilane binding outranks every heuristic label because it is deterministic; processes without a clilane record fall through to the existing chain unchanged.

The binding is stamped onto the collector's existing per-label series and existing `/api/agents` rows as attributes — never as new metric series. Per-label aggregation in `/metrics` is deliberate: pid churn and session turnover would otherwise multiply label cardinality without adding information. `task_generation`, pid, and provider-session identity may appear as fields on `/api/agents` rows, which are row-oriented and cardinality-safe; none of them may become a Prometheus label value. A deployment that needs per-session drill-down reads `/api/agents`; `/metrics` stays per-label.

The probe requires nothing from CLI Lane beyond what v0.6.0 already persists — the registry today, plus the ledger's `source_session_id` once hooks land — so it adds no phase and gates nothing in the release sequence above. It ships on agent-usage-manager's own schedule, and the telemetry exported under *Telemetry-native identity export* gives it a second, vendor-carried path to the same triple whenever a provider's OTel lane is verified.

### Phase 0 adapter gate

Before locking provider support, run executable spikes against installed Claude, Codex, and Kimi versions. For every provider and each target transition, record source API, payload identity, task and session binding, open and close semantics, reconnect behavior, provider-observation latency, and failure behavior.

Phase 0 uses a two-tier evidence boundary. Raw provider captures remain outside the repository in an operator-selected mode-0700 directory and are never required at runtime. Before any capture write, the probe resolves the worktree, Git directory, and capture root and rejects equality, containment in either direction, symlinked roots, non-directory roots, the wrong owner, or any mode other than `0700`; it has no in-repository fallback. Every capture invocation requires explicit positive per-capture and aggregate byte budgets and preflights sufficient free space for the declared run. The collector streams bytes directly to the private destination while updating SHA-256 in the same pass; it neither buffers nor rereads a complete capture to hash it. Reaching either cap records only an `incomplete` run whose provider outcome is `unknown`; truncated evidence cannot satisfy a matrix cell. The probe produces a sanitized normalized JSONL replay fixture plus a machine-readable capability matrix under version control; the design contains only a rendered human summary. Each committed row records an opaque evidence id, provider and exact version, source interface, normalized event kind, synthetic task/session/request binding, open and close behavior, duplicate and stale-session handling, reconnect and recovery result, latency samples, pass/fail/unknown status, and the SHA-256 of its private source capture. It contains no prompts, transcripts, credentials, real paths, or real session identifiers.

Phase-0 evidence code is a non-runtime Python standard-library tool under `scripts/`, not part of the shipped `bin/clilane` artifact. One shared implementation owns the normalized row schema, fail-closed sanitization and validation, deterministic ordering, matrix and design-summary rendering, and `--check`; provider-specific collectors remain thin capture inputs. The committed normalized fixture is the canonical review input, while the matrix and human summary are reproducible outputs. Production CLI Lane does not import provisional provider formats or the evidence tool.

Normalization must be deterministic and fail closed on unknown or secret-bearing fields. Canonical normalized rows use compact sorted-key UTF-8 JSON and sort by `(provider, provider_version, source_interface, event_kind, evidence_id)` before rendering. CI replays the committed fixture to regenerate the matrix and fails on drift, forbidden keys, malformed rows, unsupported schema versions, missing required cells, or a summary that disagrees with the machine-readable matrix. The private source hashes bind the reviewed normalization to the original observation without making private material a build or release dependency.

A provider is authoritative in v0.6.0 only if the spike proves exact task/session binding, open and close events for every claimed request kind, turn or terminal transitions, duplicate rejection, stale-session rejection, and recovery of unresolved requests after adapter restart. The binding decisions are recorded in the design before implementation. ACP sessions are externally launched and observed in v0.6.0 unless the spike proves CLI Lane ownership is necessary for identity or recovery. A failed provider stays attach-only and unknown.

Lane B: B1 can run in parallel with A1 through A3. B2 waits for both the installed v0.5.1 profile path and B1; only then does the integration owner add the evidence `--check` command to CI and run live captures.

Execution order: finish G0 and let the other Codex session finish G1. B1 may begin from the remote base after G0 while G1 is still active, but Lane A waits for both gates. Land or intentionally park G1, create clean worktrees from that reconciled base, then run Lane A and the remaining B1 work in parallel. Finish A4 before B2 runs live collectors and regenerates the committed matrix.

Conflict flags: the active UX session and Lane A both touch `bin/`, so T2 and T3 must not start until G1 is landed or parked and the shared base is explicit. Both later lanes add files under `tests/`, so assign one integration owner and avoid shared test helpers unless a real duplicate appears. Lane A owns `.github/workflows/smoke.yml` through the v0.5.1 release; B2 changes it only after Lane A has merged and finished, so the workflow is never edited concurrently. No lane may overwrite the active dirty `bin/clilane` worktree.
